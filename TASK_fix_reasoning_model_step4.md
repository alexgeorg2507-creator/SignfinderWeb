# TASK: Fix — убрать reasoning-модель с Шага 4 (regex generation), не поднимать max_tokens

## Контекст

Диагноз по `TASK_bugfix_llm_step4.md` подтверждён кодером: активная модель
`deepseek-v4-flash` — reasoning-модель. На Шаге 4 (генерация regex-
паттернов, `signfinder/prompts/regex_generation.py`) весь бюджет
`max_tokens=3000` уходит в `reasoning_tokens`, до видимого JSON-ответа
модель не доходит (`finish_reason=length`). Шаг 3 не задет — его промпт
короче, укладывается в 1500 токенов даже с reasoning-накладными расходами.

**Владелец явно не хочет reasoning здесь**: задача генерации regex-
паттернов механическая (структурированный вывод по чёткому промпту),
смысловой неопределённости не требует. Reasoning только тратит токены,
роняет скорость (заметно на практике) и увеличивает стоимость вызова —
`reasoning_tokens` у DeepSeek тарифицируются как обычные completion-
токены.

**Не делать:** просто поднять `max_tokens` для Шага 4. Это лечит симптом
ценой роста стоимости каждого вызова и не решает саму проблему — зачем
вообще reasoning на механическом шаге.

**Правильное решение:** сменить модель конкретно для Шага 4 (и проверить
остальные шаги пайплайна) на non-reasoning модель того же провайдера
(скорее всего `deepseek-chat`, но свериться с актуальным API DeepSeek —
имя `deepseek-v4-flash` не из моей базы знаний, состав моделей провайдера
на аккаунте нужно проверить в живой доке/дашборде DeepSeek, не гадать).

## §2. Задача

### 2.1 Определить целевую non-reasoning модель

Проверить в живой доке DeepSeek (или через `curl` к их `/models`
эндпоинту, если такой есть, с уже подключённым ключом) — какие модели
доступны, у какой нет reasoning. Кандидат по умолчанию — `deepseek-chat`,
но **подтвердить фактом, не предположением**.

### 2.2 Реализовать выбор модели per-step (если сейчас его нет)

Судя по симптому (Шаг 3 работает с reasoning-моделью нормально, Шаг 4 —
нет), возможно сейчас **одна и та же модель** используется на все шаги
пайплайна через `active_provider` в `llm_config.json`. Если так —
это архитектурное ограничение, которое стоит снять: разным шагам
пайплайна может требоваться разная модель (reasoning для смысловых
задач типа Шага 3 — если владелец решит что она там ценна; non-reasoning
для механических типа Шага 4).

Смотри `SignFinder_Concept_v2.0.md` §13 «Multi-LLM расширения» —
там уже есть пункт «Per-task выбор LLM (extraction → Claude, валидация →
DeepSeek)», помеченный «По данным cost analysis», то есть отложенная
фича. **Это тот самый момент когда данные появились** — можно её
частично приземлить, но не разворачивай в полноценный per-task-provider
фреймворк, минимальный шаг:

- Добавить в `llm_config.json` (или в вызов конкретного промпта)
  возможность явно указать модель для `regex_generation`, отдельно от
  общей `active_provider.model`
- Если это требует изменения схемы `llm_config.json` — обязательно
  обратной совместимости (старый конфиг без этого поля должен продолжать
  работать, беря дефолтную модель)
- Минимальный масштаб: **не переделывай всю архитектуру LLM-фабрики**,
  добавь точечный override для одного шага. Полноценный per-task выбор —
  отдельная задача, вне этого фикса.

Если после чтения кода окажется что per-step выбор уже есть и просто
не настроен — тогда просто настроить, ничего не разрабатывая.

### 2.3 Проверить остальные шаги пайплайна

Кодер уже отметил риск: «Шаг 3, если туда доедет та же модель на сложных
документах, тоже может упереться в лимит позже». Проверить весь пайплайн
(`extraction`, `regex_generation`, `validation`, `party_resolver`) —
для каждого шага какая модель нужна по смыслу задачи (есть ли там
реальная смысловая неопределённость, которая оправдывает reasoning, или
это тоже механический шаг). Дать короткую таблицу в отчёте — «шаг →
нужен ли reasoning → почему».

- Не поднимать `max_tokens` как решение — это симптоматическое лечение,
  явно отвергнуто владельцем
- Не переключать модель на всех шагах разом бездумно — Шаг 3 сейчас
  работает, не трогай его без обоснования из §2.3
- Не разворачивай полноценный per-task-provider фреймворк — минимальный
  точечный override, не архитектурный рефакторинг
- Не гадай имена моделей DeepSeek из памяти — проверяй в живой доке
- Не деплой на prod
- Не начинай E2 Deal Cycle пока пайплайн `/v1/me/analyze` не проходит
  стабильно на test
