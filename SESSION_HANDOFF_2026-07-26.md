## 1. Что такое Deal Cycle v2.0.0

SignFinder — B2B SaaS для автоматической расстановки подписей в PDF/DOCX
договорах. Deal Cycle — крупная версия, меняющая позиционирование с
«инструмент подписи» на «инструмент закрытия сделки»: инициатор
подписывает свою часть → передаёт временную ссылку контрагенту через
мессенджер (не email!) → контрагент подписывает без регистрации по
ссылке → оба видят финальный PDF.

**Полная спека:** `C:\work\SignfinderLand\docs\DEAL_CYCLE_SPEC.md`
(версия 1.4 на момент хендоффа) — читай целиком перед тем как
продолжать любой эпик.

**Модель угроз:** `C:\work\SignfinderLand\docs\THREAT_MODEL_DEAL_CYCLE.md`

**Ключевое архитектурное решение всей версии:** SignFinder не отправляет
email/сообщения от своего имени никому и никогда (ADR-010). Инициатор
получает ссылку и передаёт её сам через 3 кнопки (Скопировать /
Telegram / WhatsApp). Это принципиально, не обсуждается заново.

## 4. Ключевые процессные правила (уже в GIT_WORKFLOW.md, не дублирую подробно)

Полный текст — `C:\work\SignfinderLand\docs\GIT_WORKFLOW.md`. Кратко,
что важно помнить с первой секунды:

- **Правило №1 (ADR-008):** кодер деплоит на test. На prod — только
  владелец, после явного запроса и подтверждения
- **Правило №3:** промпты кодеру — только файл `TASK_*.md` в корне
  `C:\work\SignfinderLand\`, никогда текстом в чат
- **Правило №4:** «задача сделана» = сервис реально работает на
  целевом контуре, подтверждено фактами (реальные ID, реальные ответы
  API, байтовые сверки) — не «CI зелёный», не «PR открыт», не «done»
- **Правило №5:** устное «начинай X» от владельца в чате не заменяет
  TASK-файл, даже если звучит уверенно. Кодер обязан сам спросить
  файл, не полагаться что владелец/оркестратор его остановит
- **§Явные запреты:** 7 пунктов — включая «никаких локальных БД/Docker
  для тестов», «не проси/не передавай значения секретов», «мерж — не
  твоя кнопка»
- **§Journal:** реальные инциденты этой сессии записаны там как
  учебные случаи — локальный Docker (2026-07-24), CI без миграций,
  Dockerfile↔pyproject.toml рассинхрон (`nanoid` баг), устное «начинай
  E3» → код в неположенном файле

**Секреты вообще:** кодер никогда не читает и не передаёт значения
секретов. Если нужен провижининг с реальным значением (Cloud Scheduler,
новые Bot-токены) — кодер готовит точные команды с shell-подстановкой
(`$(gcloud secrets versions access ...)`), владелец выполняет сам из
своей оболочки.

## 5. Важные архитектурные поправки, сделанные по ходу (не повторяй эти ошибки)

1. **`signfinder-core` менялся один раз, с явного разрешения.** v1.21.0
   добавил резолюцию `counterparty_anchors` (якоря для стороны
   контрагента) как отдельное поле в ответе `/v1/me/analyze` — не
   фильтрация одного списка по `party_role`, как планировалось в
   исходной спеке. `DEAL_CYCLE_SPEC.md` §6 переписан под эту реальность
   (версия 1.3).

2. **Обработка подписи контрагента — отдельный публичный эндпоинт**,
   не переиспользование `/v1/signers/{tmp}/signature/process` (тот
   защищён `ApiKeyDep`, публичная страница не может держать секрет).
   Новый: `POST /v1/public/deals/{token}/signature/preview`.

3. **Веб-деплой на `git push` идёт на TEST, не на prod** — в
   `GIT_WORKFLOW.md` была обратная неточность, исправлена 2026-07-25.
   `deploy.yml` = auto → test. `deploy-prod.yml` = только вручную.

4. **APScheduler в бэкенде не работает на Cloud Run** — контейнер
   масштабируется до нуля, in-process планировщик может не сработать.
   Решение — Cloud Scheduler (внешний) → HTTP на внутренний эндпоинт,
   защищённый уже существующим `ApiKeyDep`. Провижининг застрял на
   технической проблеме с gcloud CLI (см. §3 E5) — это не архитектурная
   ошибка, чисто механика передачи заголовка.

5. **Подписанные (signed) сделки ТОЖЕ теряют PDF через 7 дней** —
   решение владельца 2026-07-26, закрывает дыру где исходный план
   исключал `signed` из зачистки (что противоречило ADR-009). Статус
   при этом не меняется на `expired`, только файлы удаляются.

## 6. Известные открытые follow-up задачи (не забыть)

- `TASK_e5_scheduler_auth_followup.md` — Cloud Scheduler не может
  передать `Authorization`-заголовок, нужен либо другой заголовок,
  либо OIDC вместо статичного токена. P2, не блокер для E6/E7, но
  нужно закрыть до реального go-live (без этого ретенция не работает
  автоматически — файлы не будут удаляться)
- Секрет `api-key` на **prod** не ротирован (в отличие от test) —
  стоит ротировать при случае, не критично
- GCS bucket `signfinder-prod-deals` с `uniformBucketLevelAccess` —
  так и не создан отдельно, всё ещё пишем в общий `signfinder-*-config`
  bucket с префиксом `deals/`. Followup из самого E1, актуален
- `Dockerfile` в `signfinder-api` всё ещё ставит зависимости
  захардкоженным списком, не через `pip install .` — известный техдолг,
  каждая новая зависимость требует ручной синхронизации с
  `pyproject.toml` (см. `GIT_WORKFLOW.md` §Известные технические дыры)
- Формулировка ПЭП-дисклеймера на публичной странице — черновик,
  требует юридического ревью перед реальным go-live (не блокер для
  разработки, блокер для публичного запуска)
