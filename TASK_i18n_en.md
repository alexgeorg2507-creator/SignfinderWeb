## §0. Архитектура — словарь строк, не дублирование файлов

`app/index.html` — 108KB, правится каждые 2-3 дня судя по истории fix15-22.
Дублирование в `app/en/index.html` означало бы каждую будущую правку
делать дважды вручную, синхронизируя руками — при нашем темпе это
развалится за пару недель. Вместо этого: один файл, JS решает какой
язык показывать, тексты вынесены в словарь.

Новый общий файл `i18n.js` (используется и `app/index.html`, и
`sign/index.html` — не дублировать механизм):

```js
const STRINGS = {
  ru: { /* все ключи */ },
  en: { /* все ключи */ },
};

let currentLang = 'ru';

function t(key) {
  return (STRINGS[currentLang] && STRINGS[currentLang][key]) || STRINGS.ru[key] || key;
}

function applyI18n(root = document) {
  root.querySelectorAll('[data-i18n]').forEach(el => { el.textContent = t(el.dataset.i18n); });
  root.querySelectorAll('[data-i18n-placeholder]').forEach(el => { el.placeholder = t(el.dataset.i18nPlaceholder); });
  root.querySelectorAll('[data-i18n-title]').forEach(el => { el.title = t(el.dataset.i18nTitle); });
}
```

**Два источника текста в текущем коде, оба нужно пройти:**
1. Статическая разметка — вешать `data-i18n="key"`, `applyI18n()` пройдёт при
   загрузке и при смене языка.
2. Текст, который JS генерирует сам (шаблонные строки внутри
   `renderScreen()` и аналогичных функций — тексты кнопок, empty-state
   карточки из fix17, тултипы тулбара, и т.д.) — там правится сам JS,
   хардкод `"Скопировать ссылку"` меняется на `${t('copy_link')}`. Это
   основной объём работы, механическая, но большая — пройти файл
   секция за секцией (шапка/нав → пустой экран → тулбар → «Мои сделки»
   → «Что улучшить?» → профиль), не пытаться одним проходом, слишком
   легко что-то пропустить.

Из скоупа: Telegram-уведомления владельцу — остаются только RU, это
внутренний инструмент, не пользовательский интерфейс. **Опросник
«Что улучшить?» изначально тоже планировался RU-only, но это
решение отменено** — владелец пересмотрел после того как увидел живой
EN-кабинет, см. `TASK_i18n_en_survey.md`.

## §1. Данные — язык пользователя и язык сделки

```sql
ALTER TABLE users ADD COLUMN language TEXT NOT NULL DEFAULT 'ru';
ALTER TABLE deals ADD COLUMN language TEXT NOT NULL DEFAULT 'ru';
```

**`users.language`** — язык по умолчанию = тот, в котором пользователь
зарегистрировался (владелец явно это попросил). Задаётся **только при
первом INSERT** в `_get_or_create_user` (`app/routers/me.py`), язык
берётся из того что прислал фронт при первом запросе (query-параметр
или заголовок — фронт знает с какого URL зашёл, `/en/app` vs `/app`).
При повторных визитах (`ON CONFLICT` ветка апсерта) **`language` не
трогать вообще** — иначе случайный заход на `/app` без префикса сотрёт
ранее сохранённое `en`. Явная смена языка — только через отдельный
эндпоинт:

```python
@router.put("/me/language", status_code=204)
async def set_language(user: UserDep, body: SetLanguageRequest) -> None:
    # body.language: Literal["ru", "en"]
    ...
```

**`deals.language`** — копируется из `initiator.language` в момент
`create_deal` (`app/routers/deals.py`), один раз, не меняется потом.
Контрагент на `/sign/{token}` получает язык интерфейса отсюда — у него
нет аккаунта, наследовать неоткуда кроме сделки. Опционально можно
дать контрагенту локальный тоггл на самой странице (не персистится,
только для этого просмотра) — не обязательно в первой итерации.

## §2. Роутинг

`firebase.json`:
```json
{ "source": "/en/app", "destination": "/app/index.html" },
{ "source": "/en/app/**", "destination": "/app/index.html" }
```
(`/app` и `/app/**` уже есть, ведут туда же — один физический файл,
язык решает JS по пути в URL при первой загрузке, дальше по значению
из БД).

`sign/{token}` — язык не зависит от URL, только от `deal.language` —
роутинг не меняется.

## §3. Переключатель в кабинете

Топбар, рядом с «Выйти» — простой RU/EN тоггл. По клику:
`PUT /v1/me/language` → обновить `currentLang` → `applyI18n()` +
перерендерить динамические секции (проще всего — вызвать тот же
`renderScreen()`/эквивалент что уже используется, не городить точечный
патчинг текстовых нод, слишком легко пропустить кусок сгенерированный
JS-ом).

## §4. `sign/index.html` — тот же механизм

Тот же `i18n.js`, тот же `data-i18n` паттерн. Язык — из
`GET /v1/public/deals/{token}` (добавить `language` в ответ, поле уже
есть в БД с §1, просто прокинуть в `DealPublicView`). Без тоггла
переключения языка в UI обязательно — по желанию, не блокирует.

**Юр. блок в финальном PDF (`_append_legal_block`, E7) — не трогать.**
Он останется на русском/ФЗ-63 независимо от языка интерфейса сделки —
это прямое следствие открытого вопроса про юрисдикцию (§0). Трогать
эту функцию только после того как юрисдикционный вопрос решится
отдельно — не раньше.

## §5. Лендинг — уже сделано, не трогать

**Проверено на факте (2026-08-XX), исходное описание ниже было неверным
— не открыл `index.html`, судил только по `firebase.json`.** У лендинга
уже есть своя независимая i18n-система (коммит `8056c38`, до начала
этой задачи): свой словарь `I18N`, свой механизм `data-i`/`setLang()`,
отдельный от `i18n.js`/`data-i18n` из §0-§4 выше. Определение языка уже
работает корректно: `/en`/`/ru` префикс пути → `sessionStorage` →
локаль браузера, в этом порядке. RU↔EN тоггл переключает всё (hero,
шаги, карточки, sandbox-демо, футер) — проверено живьём.

Ничего строить не нужно. Две системы i18n (лендинг и кабинет/sign)
остаются раздельными — не объединять ради единообразия, это не входит
в скоуп и не бесплатно.

## §6. Лег. документы — только каркас, не наполнять

Создать `terms-en.html`, `privacy-en.html`, `cookies-en.html`,
`pep-agreement-en.html` — структура/стиль как у RU-версий (которые
сейчас в долге, `TASK_fix22.md`), содержимое — **не переводить
дословно**, вместо текста плейсхолдер:

```
[EN CONTENT PENDING — юрисдикционное основание для англоязычных
контрагентов ещё не решено (см. TASK_i18n_en.md §0). Не переводить
RU-версию дословно — возможно другая юр. база, не просто языковая
разница. Ждёт отдельного решения владельца.]
```

**Не добавлять в `firebase.json` rewrites** — файлы лежат в репо,
физически недостижимы, ровно как сейчас RU-версии после `fix22`.
Когда RU разморозится и юрисдикция для EN решится — тогда и роутинг,
и контент, одним заходом.
