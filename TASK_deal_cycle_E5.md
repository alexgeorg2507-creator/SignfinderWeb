E1-E4 закрыты и подтверждены на test живыми проверками. E5 — снова

**Важно — архитектурная поправка, сделана до тебя.** Изначальный план

Вместо этого — **Cloud Scheduler → HTTP на внутренний эндпоинт**, защищённый
уже существующим `ApiKeyDep`. Полное обоснование и точный план — в
`DEAL_CYCLE_SPEC.md` §8 раздел E5 (версия 1.4) — **прочитай целиком, там
всё расписано с SQL и деталями**, этот TASK-файл дополняет, не дублирует.

**Второе решение владельца — тоже уже принято, не обсуждай заново.**
Подписанные (signed) сделки удаляют PDF через 7 дней **так же как и
незавершённые**, без исключений. Статус `signed` при этом не меняется.

## §2. Задача

### 2.1 `POST /internal/deals/expire-sweep` — часовая зачистка

Новый роутер, например `app/routers/deals_internal.py`, защищён `ApiKeyDep`.

Логика — **точно по SQL из спеки §8 E5**, вкратце:
- WHERE `expires_at < now()` И хотя бы один из трёх PDF-путей ещё не `NULL`
- Удалить реально существующие файлы из storage
- Обнулить все три path-колонки в БД
- Если `status IN ('draft','sent','viewed')` → `status='expired'` +
  событие `expired` в `audit_log`
- Если `status == 'signed'` → статус **не трогать**, добавить событие
  `files_purged` в `audit_log`
- Идемпотентность: второй вызов на той же строке не находит её под условие
  (пути уже `NULL`) — ничего не делает, не падает

Возвращает JSON-сводку, например `{"processed": 3, "files_deleted": 7}`.

### 2.2 `POST /internal/deals/purge-old` — суточная зачистка

Тот же роутер, тоже `ApiKeyDep`.

- `DELETE FROM deals WHERE expires_at + interval '30 days' < now()`
- Без учёта статуса — см. обоснование в спеке (файлы уже удалены раньше
  единым фильтром `expire-sweep`)
- Возвращает `{"deleted": N}`

### 2.3 Проверка на пустые пути перед storage-операциями

Явно проверяй `path is not None` перед вызовом `storage.delete(path)` —
не все три колонки заполнены для каждой сделки (например, у `draft`/`sent`
никогда не будет `final_pdf_path`). См. `StorageBackend` API в
`DEPLOY_CONSTRAINTS.md` — `delete(path) -> bool`, но всё равно не зови
на `None`.

### 2.4 Скрипт провизионирования Cloud Scheduler

`signfinder-api/monitoring/setup_deals_retention_cron.py` (или другое
разумное расположение по аналогии с `setup_monitoring.py`) — генерирует
две команды/вызова для создания Cloud Scheduler заданий:

- `deals-expire-sweep` — `0 * * * *` (каждый час), HTTP POST на
  `{API_URL}/internal/deals/expire-sweep`
- `deals-purge-old` — `0 3 * * *` (03:00 UTC ежедневно), HTTP POST на
  `{API_URL}/internal/deals/purge-old`

Оба — заголовок `Authorization: Bearer $(gcloud secrets versions access
latest --secret=api-key --project=<project>)` (или как у тебя принято
собирать эту команду — суть в том что **значение секрета никогда не
появляется в файле скрипта буквально**, только как shell-подстановка,
которую владелец выполнит сам).

**Скрипт коммитится в репо** (для аудита/воспроизводимости, как
`setup_monitoring.py`), но **сам вызов `gcloud scheduler jobs create`
делает владелец**, не ты — см. §3 ниже.

же IAM impersonation что раньше использовалась для JWT) — можешь
протестировать эндпоинты напрямую curl'ом на test. Если нет — тестируй
через pytest (моканный `ApiKeyDep`, как в существующих тестах
`signature_process`), это покрывает логику полностью, реальный секрет
для этого не нужен.
