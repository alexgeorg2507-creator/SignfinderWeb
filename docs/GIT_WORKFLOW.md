# SignFinder — Git-воркфлоу и CI/CD

> **Правило №1 (ADR-008):** агент деплоит на test. На prod — только человек.
>
> **Правило №2 (2026-07-04):** перед прод-деплоем агент явно пишет:
> "Фикс X на тесте стабильно. Запрашиваю деплой на прод."
> Ожидает ответа "деплой" от владельца перед любым действием на проде.
> Без подтверждения — прод не трогать. Без исключений.
>
> **Правило №3 (2026-07-24):** промпты кодеру — всегда файл `TASK_<название>.md`
> в корне `C:\work\SignfinderLand\`. Не текст в чат. Не диалог. Файл на диске.
> Кодер получает путь к файлу и читает целиком перед стартом. Все прошлые
> задачи в таком формате — см. `TASK_fix1.md`..`TASK_fix14.md`,
> `TASK_versioning.md`, `TASK_MVP_Lite_Client.md`. Причина —
> §Journal 2026-07-24, инцидент с локальным Docker.
>
> **Правило №4 (2026-07-24):** «задача сделана» = сервис реально работает
> на целевом контуре, не «PR открыт» и не «CI зелёный». После мержа кодер
> сам мониторит деплой (`gh run watch`) до успеха. Если деплой падает —
> чинит сам через код (не эскалирует владельцу «примени руками»), до 3
> итераций. Отчёт владельцу — только когда `curl /v1/version` (API) или
> живая проверка страницы (Web) на целевом контуре подтверждает новую
> версию. Причина — §Journal 2026-07-24, инцидент «deploy-test #33 упал
> после мержа E1, кодер уже вышел из активной фазы».
>
> **Правило №5 (2026-07-25):** устное «начинай X» от владельца в чате —
> НЕ заменяет TASK-файл, даже для владельца, даже под его собственным
> «эта версия стабильна, поехали». Кодер обязан сам ответить "дай
> TASK_<название>.md" и не писать код для нового эпика/фичи, пока файла
> нет — независимо от того, кто и как убедительно попросил начать
> устно. Правило №3 работает в обе стороны: не только «я всегда даю
> задачи файлом», но и «кодер всегда отказывается работать без файла».
> Причина — §Journal 2026-07-25, устное «начинай E3» → код в
> `app/index.html` до TASK-файла, владелец сам поймал и остановил.

## Ветки

```
main            — автодеплой на test при каждом merge. Живая ветка разработки.
feature/*       — фичи, PR в main
hotfix/*        — срочные фиксы, PR в main с приоритетным ревью
release/*       — заморозка перед крупным prod-релизом (опционально)
```

Прямые пуши в `main` — запрещены. Всегда через PR, даже если ревьюер — ты сам.
**PR мержит владелец** — даже когда CI зелёный и агент технически мог бы. Не
спрашивать «мержить самому?» — ответ всегда «нет», см. Правило №1/ADR-008.

Правило одинаково для **обоих** репозиториев — `signfinder-api` и веб-клиент
(локальная папка `SignfinderLand`, git remote `SignfinderWeb`).

## Definition of Done для PR

- [ ] CI зелёный (18 существующих тестов + новые из TASK-файла, см. `RUNBOOK_TESTING.md`)
- [ ] Если менялась схема БД — Alembic-миграция есть (`alembic revision -m "..."`)
- [ ] Если новый эндпоинт — ИБ-чеклист (ADR-007): 401 без токена, данные только из JWT, `extra='forbid'`
- [ ] Если менялась версия `signfinder-core` — версия забампана (`pyproject.toml` + `__init__.py`)
- [ ] Если менялась версия `signfinder-api` — `pyproject.toml` единственное место
- [ ] Если менялся веб-клиент — `version.txt` в `SignfinderLand/` забампан
- [ ] **Если добавлена новая Python-зависимость — сверена в ДВУХ местах:**
  `pyproject.toml` (`dependencies`) И `Dockerfile` (`RUN pip install` список).
  Они не связаны автоматически — см. §Известные технические дыры, пункт 1.
- [ ] Диф прочитан целиком
- [ ] `conftest.py`, `alembic.ini`, `pyproject.toml` dev-deps не менялись «под локальный запуск» (см. §Явные запреты)
- [ ] После мержа — деплой на test реально дошёл до конца, не только PR смёржен
  (см. Правило №4)

## §Явные запреты — что НЕ делать никогда

Эти правила не «best practice» и не «желательно». Это жёсткие запреты.
Ссылки на них в промптах — «см. GIT_WORKFLOW § Явные запреты, пункт N».

### 1. Локальные БД для тестов — запрещены

Никакого локального Postgres, SQLite, встроенных БД, in-memory БД.
Тесты гоняются только против `signfinder-cab-test` через CI.

**Никаких:**
- `docker run postgres`
- `docker-compose up` с postgres/redis/etc в CI-пайплайне
- `sqlite:///:memory:` в `conftest.py` под предлогом «для быстроты»
- Установки `pg_ctl start` локально
- Testcontainers, pytest-postgresql, любых аналогов

**Если тесты не запускаются локально — это НЕ баг. Это дизайн.**

Локальная БД = ещё одна среда со своей схемой, своими данными, своими расхождениями с реальным test. Ровно то, от чего защищает ADR-004 (две изолированные среды).

### 2. `conftest.py`, `alembic.ini`, `pyproject.toml` dev-dependencies — не трогать

Эти файлы написаны под работу с cloud-sql-proxy и CI. Любая правка «под локальный запуск» ломает CI. Если хочется что-то поменять — сначала спрашиваешь владельца, зачем и как это переживёт CI.

### 3. `docker run` для сервисов проекта — запрещён

Postgres, Redis, RabbitMQ, любые другие сервисы — только в проектных средах (test/prod). Локально не поднимаются никогда.

Docker для сборки проектного образа (`docker build`, `docker buildx`) — разрешён, это часть штатного пайплайна. Разница — сборка артефакта vs запуск сервиса.

### 4. Обход классификатора / просьбы «дай пароль» — запрещены

Если инструмент говорит «доступ заблокирован» — это правильно. Не проси владельца дать пароль от Secret Manager, не проси выключить защиту, не проси экспортировать SA-ключ на диск.

Правильная реакция — «работаю через CI, у CI есть свой доступ через `GOOGLE_CREDENTIALS_TEST`». Всё.

### 5. Ручные шаги «применить миграцию», «настроить bucket», «положить секрет» — не выдумывать

Если чего-то не хватает в автоматизации (миграции не применяются в CI, bucket не создан, секрет не подключён к Cloud Run) — **это баг существующей автоматизации**. Чинишь его в её же контуре (`ci.yml`, `cloudbuild-*.yaml`, `setup_monitoring.py`), не в обход через ручные инструкции владельцу.

Владельца тревожишь только за: (a) деплой на prod, (b) продуктовые решения, (c) архитектурные развилки. Инфру и CI чинишь сам через код.

### 6. Мерж PR — не твоя кнопка

Не спрашивай «мержить самому?» и не мержи даже если технически можешь. Открыл PR, CI зелёный — сообщил владельцу и ждёшь. Мерж — его действие всегда, без исключений (ADR-008).

### 7. `workflow_dispatch` (ручные прод-деплои) — не запускай сам

`deploy-prod.yml` в обоих репозиториях (`signfinder-api` и веб-клиент) запускается только вручную через GitHub UI/CLI по `workflow_dispatch`. Не вызывай `gh workflow run deploy-prod.yml` сам ни в каком репозитории — это ровно то нажатие кнопки, которое зарезервировано за владельцем (Правило №1/№2).

## §Не изобретай инфраструктуру

Вся инфраструктура проекта уже спроектирована. Если чего-то нет — это дыра, не свобода.

**Спроектировано:**
- Два GCP-проекта (test/prod) — ADR-004
- Auth через Firebase — ADR-003
- Storage через существующий `StorageBackend` — `signfinder-core/signfinder/storage/base.py`
- CI/CD через GitHub Actions (`ci.yml`, `deploy-test.yml`, `deploy-prod.yml` в обоих репо) — этот файл
- Мониторинг через `signfinder-api/monitoring/setup_monitoring.py`
- Секреты через Secret Manager — `SECRETS_REGISTRY.md`
- Миграции через Alembic — этот файл, §Миграции БД
- Веб-хостинг через Firebase Hosting, роутинг через `firebase.json` `rewrites` —
  этот файл, §CI/CD, блок Web

**Не изобретаешь:**
- Новый способ хранить данные (свой S3, свой Redis, свой SQLite)
- Новый способ деплоя (свой скрипт вместо GitHub Actions)
- Новый способ тестирования (свой docker-compose с БД)
- Новый способ управления секретами (свой .env файл в репо)
- Свой формат миграций (голые `.sql` вместо Alembic)
- Свой сервер/роутинг для новых веб-страниц вместо Firebase Hosting rewrites

Если что-то из существующего не работает или не хватает — **правишь существующее в его же контуре**, не создаёшь параллельное.

Пример правильного: миграции не применяются в CI → правишь `ci.yml`, добавляешь `alembic upgrade head` шагом перед `pytest`. Копируешь паттерн из `deploy-prod.yml` (где это уже есть).

Пример неправильного: миграции не применяются в CI → «а давай локально Postgres поднимем и там прогоним». Это не решение проблемы, это её обход через новую параллельную инфру, которую потом придётся поддерживать.

Пример правильного для веб-клиента: нужна новая публичная страница по пути
`/foo/{id}` → добавляешь `rewrite` в `firebase.json` + новый статический
HTML-файл в соответствующей директории, по образцу существующего `/app`
(`{ "source": "/app/**", "destination": "/app/index.html" }`). Не поднимаешь
отдельный сервер, не меняешь модель хостинга.

## §Известные технические дыры (проверять при каждом PR)

Список мест где инфраструктура ломается тихо — не падает при коммите,
падает позже на деплое. Каждый пункт — реальный инцидент.

### 1. `Dockerfile` не связан с `pyproject.toml` (signfinder-api)

`signfinder-api/Dockerfile` ставит зависимости захардкоженным списком:

```dockerfile
RUN pip install --no-cache-dir \
    "fastapi>=0.115" \
    "uvicorn[standard]>=0.32" \
    ...
```

Это **не** `pip install .` — значит `pyproject.toml` и Dockerfile надо
синхронизировать руками. Добавил зависимость в одно место — обязан
добавить и в другое. Не свяжешь — CI зелёный (тесты гоняются из
`pyproject.toml`-окружения), а `deploy-test.yml`/`deploy-prod.yml` падает
(Cloud Run образ собран без зависимости, `ModuleNotFoundError` при старте).

**Инцидент:** E1 (2026-07-24) — `nanoid` добавлен в `pyproject.toml`, забыт
в Dockerfile → CI зелёный → `deploy-test.yml #33` упал в crash loop.

**Правило:** при любой новой зависимости — сверять оба места, это пункт
Definition of Done для PR (см. выше). Рефактор на `pip install .` —
отдельный TASK, записан в `BACKLOG.md` как техдолг, не делать походя.

## CI/CD — полная схема

Два независимых репозитория, каждый со своим test/prod разделением.

```
┌─────────────────────────────────────────────────────────────────┐
│  Репо: signfinder-api                                           │
│                                                                  │
│  git push → main                                                 │
│      │                                                           │
│      ▼                                                           │
│  ci.yml (авто)                                                   │
│  ├── pip install + signfinder-core@github/main                   │
│  ├── cloud-sql-proxy → signfinder-cab-test DB                    │
│  ├── alembic upgrade head (добавлено 2026-07-24 в PR E1)        │
│  ├── pytest 18+ тестов → JUnit XML artifact                     │
│  └── pass →                                                      │
│      ▼                                                           │
│  deploy-test.yml (авто, после ci.yml)                           │
│  ├── gcloud builds submit cloudbuild-test.yaml                   │
│  ├── smoke: /health → 200, /v1/me/profile → 401                 │
│  └── логирует версии из /v1/version                             │
│                                                                  │
│  deploy-prod.yml (ТОЛЬКО вручную, workflow_dispatch)            │
│  ├── alembic upgrade head (prod DB)                              │
│  ├── gcloud builds submit cloudbuild-prod.yaml                   │
│  ├── smoke: /health → 200, /v1/me/profile → 401                 │
│  └── Telegram: ✅ API vX.Y + Core vX.Y                          │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│  Репо: SignfinderWeb (локальная папка C:\work\SignfinderLand)   │
│                                                                  │
│  git push → main                                                 │
│      │                                                           │
│      ▼                                                           │
│  deploy.yml (авто) — ⚠️ деплоит на TEST, не на prod             │
│  ├── inject window.__SF_VERSION__ из version.txt в app/index.html│
│  ├── firebase deploy --only hosting --project=signfinder-cab-test│
│  └── Нет Telegram-нотификации на этом шаге (см. ниже)            │
│                                                                  │
│  deploy-prod.yml (ТОЛЬКО вручную, workflow_dispatch)            │
│  ├── та же инъекция версии                                       │
│  ├── firebase deploy --only hosting --project=signfinder-prod   │
│  └── Telegram: ✅/🚨 PROD — Web deployed vX.Y → signfinder.app  │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│  signfinder-core — НЕ деплоится отдельно                        │
│  Подтягивается при каждой сборке api:                           │
│  Dockerfile: pip install из github.com/...signfinder-core@main  │
│  Версия видна в /v1/version → signfinder_core_version           │
└─────────────────────────────────────────────────────────────────┘
```

**Веб-клиент симметричен API-репозиторию** — push в main = авто-деплой
на test-проект (`signfinder-cab-test`), прод — только ручной
`workflow_dispatch`. Раньше в этом документе была неточность (написано
что `deploy.yml` деплоит сразу на `signfinder-prod`) — исправлено
2026-07-25 после проверки фактического `.github/workflows/deploy.yml`.

## Версии — где живут и как менять

| Компонент | Файл | Как |
|-----------|------|-----|
| `signfinder-api` | `signfinder-api/pyproject.toml`, поле `version` | Вручную перед деплоем. Единственное место. |
| `signfinder-core` | `signfinder-core/pyproject.toml` + `signfinder/__init__.py` | При каждом коммите в core. Оба файла. |

## Деплой на prod — чеклист перед нажатием кнопки

**API (`signfinder-api`):**
1. CI зелёный на `main`
2. `deploy-test.yml` прошёл + smoke test
3. Ручная проверка на test: логин → профиль → подпись → договор → скачать
4. `git log` — посмотреть что идёт в деплой
5. GitHub Actions → `deploy-prod.yml` → Run workflow
6. Пришло Telegram ✅ с версиями
7. `git tag prod-YYYY-MM-DD && git push --tags`
8. Обновить журнал ниже

**Web (веб-клиент, репо `SignfinderWeb`):**
1. Поправить `version.txt` если нужна новая версия
2. `git push` в `main` → `deploy.yml` запускается автоматически, но деплоит
   **на test** (`signfinder-cab-test`) — это не финальный шаг, это обычный
   деплой на test-контур как для любой фичи
3. Проверить test: `https://<test-hosting-url>/app` — бейдж версии в topbar
4. Только после проверки на test — GitHub Actions → `deploy-prod.yml` →
   Run workflow (ручной запуск, только владелец, см. §Явные запреты пункт 7)
5. Пришло Telegram ✅ с Web версией
6. Проверить `signfinder.app` в браузере — бейдж версии в topbar

## Миграции БД

```powershell
alembic revision -m "describe_change"   # создать
alembic upgrade head                     # применить
alembic downgrade -1                     # откатить на шаг
alembic current                          # текущее состояние
alembic stamp head                       # fake-apply на существующей БД
```

**`ci.yml` применяет миграции автоматически** перед `pytest` (шаг добавлен 2026-07-24 в PR E1).
**`deploy-prod.yml` применяет миграции автоматически** перед сборкой прод-образа.

Владелец руками миграции не применяет никогда. Если тебе говорят «примени миграцию сам» — это неверная инструкция, чини автоматизацию.

Локально миграции гоняются только против `signfinder-cab-test` через cloud-sql-proxy — то есть только если у тебя есть `gcloud auth`-сессия. Как правило, у агента её нет — значит миграции гоняются только в CI.

## Rollback

**API (секунды):**
```powershell
gcloud run services update-traffic signfinder-api `
  --to-revisions=PREVIOUS_REVISION=100 --project=signfinder-prod --region=europe-west1
```

**Web:**
```powershell
firebase hosting:clone SOURCE_VERSION signfinder-prod:live
```

**БД:** `DB_SCHEMA_AND_BACKUP.md`. Деструктивные миграции требуют `downgrade()`.

классификатор при попытке гонять тесты локально (нет доступа к Secret

кодер поднял локальный Postgres 15 в Docker, начал модифицировать
`conftest.py` под `DATABASE_URL`-override. Владелец остановил, откатил.

**Что пошло не так на моей стороне** (промпт-инженер, Opus 4.7):
1. В промпте не было явного запрета на локальный Docker/БД.
2. Когда кодер спросил «как проверить код?», я в реальном времени предложил
   локальный Postgres как «fallback для быстроты» — ровно то что противоречит
   `GIT_WORKFLOW.md`. Это отсебятина, её не было в правилах проекта.
3. Промпт был выдан текстом в чат, а не файлом на диске — вопреки
   существующей практике всех предыдущих задач (`TASK_*.md` в
   `SignfinderLand/`).

**Что пошло не так на стороне кодера.**
1. Не прочитал `GIT_WORKFLOW.md` до старта, пошёл сразу писать код.
2. Инженерный рефлекс «эффективно решить задачу» → локальная среда как
   стандартный шаблон. Не запрещено = разрешено.

**Уроки формализованы:**
- Правило №3 (промпты как файлы) — этот документ, шапка.
- §Явные запреты — этот документ, добавлено.
- §Не изобретай инфраструктуру — этот документ, добавлено.
- Шаблон TASK-файла требует обязательного reading gate первым действием
  и явной строки-подтверждения «прочитал GIT_WORKFLOW § Явные запреты,
  локальный Docker/БД не будет». Без этой строки код не начинается.

### 2026-07-24 — CI не применял миграции

**Что случилось.** При E1 (миграция 003_deals) тесты в CI упали с
`UndefinedTableError: relation "deals" does not exist`. Причина —
`ci.yml` гонял pytest без `alembic upgrade head`, миграция не
применялась на test-БД. `deploy-prod.yml` этот шаг имел, `ci.yml` — нет.
Дыра существовала с 2026-07-03 (инициализация Alembic), проявилась на
первой же новой миграции.

**Что пошло не так на моей стороне.**
1. При составлении промпта E1 я не проверил `ci.yml` на наличие
   `alembic upgrade head`. Полагался на общее упоминание «Alembic
   инициализирован» в BACKLOG.
2. Когда кодер эскалировал «как применить миграцию?», моей первой
   формулировкой было «спроси владельца» — это неверно, миграции
   применяются автоматизацией, не человеком.

**Что пошло не так на стороне кодера.**
1. Не заметил отсутствие шага в `ci.yml` при первом чтении.
2. Первым инстинктом эскалировал владельцу, а не разобрался что
   починить в CI.

**Уроки формализованы:**
- §Миграции БД — этот документ, добавлено «CI применяет миграции
  автоматически, владелец руками — никогда».
- §Не изобретай инфраструктуру — этот документ, пример «CI не
  применяет миграции → правишь `ci.yml`, не обходишь».
- В шаблоне TASK-файла добавлен пункт «прочитать все `.yml` в
  `.github/workflows/` до старта, понять что автоматизировано,
  найти дыры в существующем контуре — их чинишь ты, не эскалируешь».

### 2026-07-24 — `deploy-test.yml` упал после мержа E1 (Dockerfile ↔ pyproject.toml)

**Что случилось.** E1 смёржен, CI был зелёным. `deploy-test.yml #33`
упал на шаге деплоя в Cloud Run — контейнер не стартовал
(`ModuleNotFoundError: No module named 'nanoid'`). Причина: `nanoid`
добавлен в `pyproject.toml` (используется тестами через CI-окружение),
но не добавлен в захардкоженный список `pip install` в `Dockerfile`.
Владелец обнаружил падение сам, спросил «что мешает агенту смотреть
результаты — все права есть».

**Что пошло не так на моей стороне.**
1. В промпте E1 не было пункта «сверить Dockerfile и pyproject.toml».
2. Не было явного правила «кодер мониторит деплой после мержа» —
   кодер отчитался «PR открыт, CI зелёный» и вышел из активной фазы
   до того как реально проверил что сервис задеплоился и работает.
   CI-зелёный ≠ задеплоено. Это разные этапы пайплайна.

**Что пошло не так на стороне кодера.**
Технически ничего — у него действительно не было явной инструкции
мониторить `deploy-test.yml` после мержа (это делает GitHub Actions
автоматически, кодер не участвует если его не попросили). Отчитался
по букве TASK-файла, где DoD заканчивался на «CI зелёный, PR открыт».

**Уроки формализованы:**
- **Правило №4** — этот документ, шапка. «Задача сделана» = сервис
  реально работает на целевом контуре, не «PR открыт».
- §Известные технические дыры, пункт 1 — этот документ, добавлено.
- Definition of Done для PR — добавлен пункт про сверку
  Dockerfile/pyproject.toml.
- В шаблоне TASK-файла: после мержа кодер обязан мониторить
  `deploy-test.yml` (`gh run watch`) до успеха, чинить падения сам
  (до 3 итераций), отчитываться только когда `curl /v1/version`
  подтверждает новую версию на целевом контуре.

### 2026-07-25 — Неточность в этом документе: веб-деплой на push шёл на test, не на prod

**Что случилось.** При подготовке TASK на эпик E2 (первая задача,
трогающая веб-клиент) обнаружено расхождение: этот документ утверждал
что `deploy.yml` в веб-репозитории деплоит `git push → main` сразу на
`signfinder-prod`. Проверка фактического
`SignfinderLand/.github/workflows/deploy.yml` показала — деплой идёт на
`signfinder-cab-test` (`projectId: signfinder-cab-test`). Прод-деплой веба
происходит только через отдельный `deploy-prod.yml`
(`workflow_dispatch`), симметрично API-репозиторию. Ошибки в проде не
случилось — расхождение поймано на этапе чтения документации, до начала
работы над E2.

**Что пошло не так.** Документ описывал схему веб-деплоя со слов, без
проверки фактического YAML на момент написания (2026-07-04). За три
недели либо схема изменилась, либо была неточно задокументирована
изначально — не выяснено какое из двух, не критично.

**Урок формализован:** при любой правке TASK-файла или документации,
затрагивающей CI/CD — сверять с фактическим `.yml`, не полагаться на
память/более раннюю версию документа. Раздел §CI/CD исправлен на факт
2026-07-25.

### 2026-07-25 — Устное «начинай E3» обошло TASK-файл, код попал в `app/index.html`

**Что случилось.** Во время живой сессии владелец сказал кодеру устно
«начинай E3 — эта версия стабильна», без TASK-файла. Кодер начал
реализовывать логику передачи сделки прямо в `app/index.html` — файле, который
текущий TASK-файл эпика E2 явно просил не трогать. Владелец сам заметил,
написал «стоп. нет задачи на E3? сейчас сделаем. жди.» — кодер остановился.
Код остался незакоммиченным, ни в одной ветке, без эффекта на test/prod.

**Что пошло не так на стороне кодера.** По собственному признанию кодера:
следовало сразу отказаться писать код и попросить TASK-файл, вместо того
чтобы владелец сам ловил нарушение постфактум. Устное разрешение от
владельца ощущается как весомое — особенно когда оно звучит уверенно после
долгой успешной сессии — но это не то же самое что формальный артефакт
(TASK-файл), который можно перечитать, сверить, на который можно сослаться в
DoD.

**Уроки формализованы:**
- **Правило №5** — этот документ, шапка. Кодер сам отказывается работать
  без TASK-файла, независимо от того кто и как убедительно попросил начать устно.
- Незакоммиченный код после такого инцидента — не выбрасывается автоматически,
  но и не считается частью какого-либо эпика пока не пересмотрен против
  формальной спекой когда она появится.
