# Threat Model — SignfinderLand v2.0.0 Deal Cycle

> Модель угроз публичной страницы подписания и связанных с ней потоков
> данных. Формат — компактный, ориентирован на MVP: разбор поверхности
> атаки анонимного контрагента, оценка митигаций, явный список
> остаточных рисков.
>
> **Связан со спекой:** `DEAL_CYCLE_SPEC.md` (v1.2 и выше).
> **Связан с ADR:** ADR-007 (три принципа security), ADR-009 (7-дневное
> хранение PDF), ADR-010 (отказ от backend-рассылок).

---

## 1. Границы и актёры

**Актёры:**

| Актёр | Аутентификация | Что имеет |
|-------|----------------|-----------|
| Инициатор | Firebase JWT | `tenant_id`, свой список сделок, приватные API `/v1/me/*` и `/v1/deals/*` |
| Контрагент | Нет | Один `share_token` в URL. Больше ничего |
| Аноним (тот кто натыкается на публичную ссылку случайно) | Нет | Аналогично контрагенту — они технически одно и то же лицо для системы |
| Атакующий (внешний) | Нет / любая | Пробует подобрать share_token или обойти проверки |

**Границы доверия (Trust boundaries):**

```
┌───────────────────────────────────────────────────────────────┐
│  Публичный интернет (не доверенная зона)                      │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐         │
│  │  Инициатор   │  │  Контрагент  │  │  Атакующий   │         │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘         │
│         │ JWT             │ share_token     │ ничего/подбор   │
│         └───────┬─────────┴──────────┬──────┘                 │
│                 │                    │                        │
│═════════════════│════════════════════│════════════════════════│
│                 ▼                    ▼                        │
│         Cloud Run (SignfinderLand backend)                    │
│         ┌──────────────────┐  ┌──────────────────┐            │
│         │ Приватные /v1/me │  │ Публичные        │            │
│         │ + /v1/deals      │  │ /v1/public/deals │            │
│         │ Firebase Auth    │  │ share_token      │            │
│         └────────┬─────────┘  └────────┬─────────┘            │
│                  └────────┬────────────┘                      │
│                           ▼                                   │
│         ┌───────────────────────────────────┐                 │
│         │ Cloud SQL (deals, users, ...)     │                 │
│         │ GCS deals/{deal_id}/*.pdf         │                 │
│         │ (доверенные, доступ только через  │                 │
│         │  backend, не напрямую)            │                 │
│         └───────────────────────────────────┘                 │
└───────────────────────────────────────────────────────────────┘
```

**Ключевой принцип:** контрагент никогда не пересекает границу приватного
API. Всё что он видит — то что backend осознанно отдал через публичный
эндпоинт с проверкой share_token.

## 2. Активы (что защищаем)

| Актив | Классификация | Кто может видеть |
|-------|---------------|------------------|
| `firebase_uid` / `tenant_id` инициатора | Личный идентификатор | Никто кроме владельца JWT |
| Email инициатора | PII (личный) | Осознанно раскрывается контрагенту («Договор от …») |
| Профиль инициатора (ФИО, компания, реквизиты) | PII | Никто кроме владельца JWT |
| Список сделок инициатора | Метаданные бизнеса | Никто кроме владельца JWT |
| Оригинал PDF договора (`original.pdf`) | Юр. документ | Только инициатор через `/v1/deals/{id}` |
| PDF со стороной инициатора (`initiator_signed.pdf`) | Юр. документ, содержит подпись | Только владелец share_token (через публичный API) |
| Финальный PDF (`final.pdf`) | Юр. документ, содержит IP+timestamps обеих сторон | Владелец share_token 7 дней, инициатор через свой кабинет |
| Chat_id владельца в Telegram | Метаданные | Только в Secret Manager, никуда не раскрывается |

## 3. Разбор угроз

Каждой угрозе присвоена метка **A**–**H** для удобства ссылок в коде и PR.

### A. Bruteforce чужого share_token

**Атака:** попытаться подобрать валидный share_token и получить доступ к
чужой сделке.

**Митигация:**
- share_token: nanoid 32 символа, алфавит `A-Za-z0-9_-` (энтропия ~192 бита).
  Криптостойкий RNG (`nanoid.generate()` в Python — использует `secrets`).
- Rate limit публичных эндпоинтов: 10 req/min на share_token, 60 req/min на
  IP. Реализация — SlowAPI поверх FastAPI, ключ — реальный IP из
  `X-Forwarded-For` (Cloud Run) с fallback на RemoteAddr.
- Неверный token → 404 (не 403), чтобы не подтверждать факт существования.

**Остаточный риск:** пренебрежимый. При 60 req/min из одного источника
полный перебор занимает больше времени существования Вселенной.

**Статус:** ✅ Митигировано.

---

### B. IDOR через подмену ID в теле POST /sign

**Атака:** контрагент делает POST на свой валидный `/sign`, но в теле
передаёт `deal_id` или `tenant_id` чужой сделки, надеясь на race в коде
типа «взять tenant_id из body если пришёл».

**Митигация:**
- Идентификатор сделки берётся **только из URL** (share_token), никогда из
  body — прописано в спеке §5.7, обязательный код-ревью каждого публичного
  эндпоинта.
- Pydantic-схема `DealSignRequest` с `extra='forbid'` — не пропустит лишние
  поля. Тест `test_sign_extra_fields_422` в списке v2.0.0-тестов.
- `initiator_tenant_id` не является полем ни одной public-запроса
  Pydantic-схемы вообще.

**Остаточный риск:** отсутствует при корректной реализации. Ловится
integration-тестом.

**Статус:** ✅ Митигировано при правильной реализации, проверяется тестами.

---

### C. Enumeration чужих сделок инициатора

**Атака:** зная одну ссылку от Пети, узнать список всех остальных сделок Пети.

**Митигация:**
- Публичного `list deals` не существует.
- Search по share_token не поддерживается.
- Из share_token невозможно вывести другие share_token (они независимо
  сгенерированные nanoid).
- Приватный `GET /v1/deals` требует Firebase JWT — контрагент не имеет.
- `DealPublicView` не содержит `initiator_tenant_id`, поэтому даже если
  контрагент угадает как коррелировать сделки — не с чем.

**Остаточный риск:** отсутствует.

**Статус:** ✅ Митигировано.

---

### D. Прямой доступ к storage мимо backend

**Атака:** зная UUID сделки, попытаться дёрнуть PDF напрямую из GCS через
публичный URL типа `https://storage.googleapis.com/signfinder-prod-deals/deals/{uuid}/original.pdf`.

**Митигация:**
- GCS bucket `signfinder-prod-deals` создаётся с `uniformBucketLevelAccess: true`.
- IAM: доступ только у service account Cloud Run.
- Никаких публичных ACL. Никаких signed URLs с TTL — все файлы идут через
  backend с проверкой share_token.
- Инфраструктурный тест: при создании bucket'а — `gsutil iam get` не
  содержит `allUsers` / `allAuthenticatedUsers`. Записать в
  `signfinder-api/monitoring/setup_monitoring.py` или отдельный
  `setup_storage.py`.

**Остаточный риск:** если разработчик руками поменяет bucket ACL — Falcon
никак не защищён. Смягчение: quarterly audit `gsutil iam get` вручную,
плюс алерт если bucket становится публичным (Cloud Asset Inventory
notification).

**Статус:** ✅ Митигировано на уровне инфры, требует дисциплины при
изменениях.

---

### E. Race condition двойной подписи

**Атака:** контрагент (или атакующий, если каким-то образом получил
share_token) делает два параллельных POST /sign, надеясь что второй
перезапишет данные первого.

**Митигация:**

Атомарное обновление с проверкой статуса:

```sql
UPDATE deals
SET status='signed',
    final_pdf_path=$1,
    counterparty_signature_meta=$2,
    audit_log = audit_log || jsonb_build_object(...)
WHERE share_token=$3
  AND status IN ('sent','viewed')
RETURNING id;
```

Если строк не обновилось (уже signed / expired / rejected) — второй запрос
возвращает 409 Conflict.

**Остаточный риск:** отсутствует при использовании транзакций Postgres.

**Статус:** ✅ Митигировано.

---

### F. Что контрагент видит про инициатора

Не атака, а осознанное решение о раскрытии.

**Что публичный API отдаёт:**
- Email инициатора, для отображения «Договор от …» (обязательно чтобы
  контрагент мог опознать отправителя)
- Статус сделки
- Ссылки на скачивание PDF
- `expires_at`
- Якоря **только для стороны контрагента** (`saved_anchors`
  фильтруются по `party_role` перед отдачей)

**Что публичный API НЕ отдаёт:**
- `initiator_tenant_id`, `initiator_firebase_uid`
- Профиль инициатора (ФИО, компания, реквизиты)
- Другие сделки инициатора
- Якоря инициатора
- Полный audit_log (только упрощённый: created / viewed / signed без IP+UA)

**Реализация:** Pydantic-схема `DealPublicView` с явным whitelist полей.
Тест: `test_public_view_no_sensitive_fields` — проверяет что в ответе нет
`initiator_tenant_id`, `initiator_firebase_uid` и т.д.

**Остаточный риск:** email — это PII. Если инициатор использует
корпоративный email (`alexander@company.com`) — контрагент видит компанию.
Смягчение: опциональная маскировка (`a***@company.com`) или отдельное
поле «Отображаемое имя» в профиле — вопрос v2.1, не сейчас.

**Статус:** ✅ Осознанное раскрытие в минимальном объёме.

### G. Реюз ссылки после подписания

**Атака:** любой кому Петя переслал ссылку (или кто увидел её в общем
чате) в течение 7 дней после signed может открыть страницу и скачать
финальный PDF с IP+timestamps обеих сторон в юр. блоке.

**Митигация:** осознанное решение — Вариант 1 из обсуждения 2026-07-23.
Ссылка живёт 7 дней и после signed, PDF viewer + кнопка «Скачать»
доступны любому обладателю share_token. Причины:
- Кто теоретически увидит эту ссылку кроме контрагента — только те, кому
  инициатор или контрагент сами её переслали. Это не «утечка» в юр. смысле.
- Контрагенту нужна возможность вернуться и скачать финальный PDF если он
  случайно закрыл вкладку.
- Одноразовое скачивание (Вариант 3) — плохой UX: закрыл вкладку → потерял
  файл.
- Приватизация через логин контрагента после signed — не MVP, ломает
  принцип «без регистрации».

**Что явно указано в Privacy Policy** (обязательно при первом go-live):

> Ссылка на подписанный документ действует в течение 7 дней после подписания.
> Переслав эту ссылку третьим лицам, вы делитесь с ними возможностью видеть
> финальный подписанный документ, включая юридический блок с IP-адресами
> и временем подписания обеих сторон.

**Остаточный риск:** принят.

**Статус:** ✅ Осознанное решение с явной коммуникацией пользователю.

---

### H. XSS / prompt injection через содержимое PDF или имя инициатора

**Атака:** вставить в PDF или в email инициатора JS/HTML, надеясь на
исполнение при рендеринге на публичной странице.

**Митигация:**
- pdf.js рендерит PDF в sandbox, JS внутри PDF не исполняется.
- Email инициатора отображается через text-content, не innerHTML.
- Pydantic валидирует email по стандарту, отклоняет невалидные (включая
  большинство инъекционных payload).
- Response headers: `Content-Security-Policy` с `default-src 'self'`,
  `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` (страница не
  должна открываться в iframe).
- Содержимое PDF инициатор загрузил сам осознанно; инъекция через PDF —
  атака самого инициатора на самого себя. Не в модели угроз.

**Остаточный риск:** отсутствует при корректной реализации CSP и
использовании text-content.

**Статус:** ✅ Митигировано.

## 4. Остаточные риски (принимаем)

1. **Утечка share_token через мессенджер** — если сам инициатор или
   контрагент переслал ссылку не тому, это не техническая уязвимость.
   Смягчение: короткий срок жизни (7 дней).

2. **Скриншот-утечка** — контрагент может сделать скриншот подписанного
   PDF и распространить его. Технически не защитимо. Не в скоупе.

3. **Компрометация Firebase-аккаунта инициатора** — если Петя потерял
   доступ к своему email/Google-аккаунту, атакующий может создать сделку от
   его имени. Смягчение: 2FA у самого пользователя, не наша ответственность.

4. **Отказ от email-канала как следствие ADR-010** — инициатор не узнает
   о статусе сделки без визита в кабинет. Смягчение: явное решение в
   ADR-010, компенсируется опциональным бейджем в topbar.

5. **Manipulation ЮР. блока** — теоретически можно склонить контрагента
   подписать через VPN так, чтобы IP в юр. блоке был не его настоящий.
   Смягчение: юр. блок фиксирует IP как факт («подписано с IP X»), не
   утверждает что это домашний адрес подписанта. Юр. трактовка ПЭП
   допускает такую неточность.

## 5. Явно вне модели угроз

- DDoS на публичную страницу — Cloud Run автомасштабируется, стоимость
  атаки для нападающего высокая, ущерб — недоступность, не утечка.
- Юрисдикционные вопросы (ФЗ-63 vs GDPR vs польское право) — не техника,
  требует юр. review.
- Insider threat (владелец имеет доступ ко всем данным) — принято,
  single-tenant per user, self-hosted-как-услуга.
- Атаки на signfinder-api / signfinder-core — отдельные модели угроз этих
  сервисов, здесь не разбираем. Deal Cycle только дёргает существующие
  `/v1/analyze` и `/v1/sign`.
