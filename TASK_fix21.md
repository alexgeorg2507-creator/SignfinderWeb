# TASK: Fix-21 — гейт принятия условий при логине

> Найдено владельцем: три юр. документа написаны и доступны по прямым
> URL (`TASK_fix20.md`), но нигде на сайте пользователь не должен их
> принять — просто висят в футере, кто заметил тот заметил. Нужен
> блокирующий шаг, как уже есть для email-верификации.

## §1. Миграция

```sql
ALTER TABLE users ADD COLUMN terms_acceptance_log JSONB NOT NULL DEFAULT '[]';
```

**Не плоские `terms_accepted_at`/`terms_version`, а журнал** — тот же
паттерн что `deals.audit_log` из E7 (IP/UA инициатора/контрагента в
юр. блоке финального PDF), не изобретать второй. Причина не просто
соответствие стилю: если позже версия документов изменится и пользователь
перепримет снова, одиночные поля без истории просто затрут что человек
реально принял в момент когда действовала старая версия. Журнал
сохраняет это навсегда, новое принятие — append, не overwrite.

Один чекбокс на все три документа разом (оферта+конфиденциальность+
cookies публикуются и версионируются как один пакет, отдельно каждый не
трогаем) — тот же принцип что уже у чекбокса ПЭП на `/sign/{token}`:
один чекбокс, один факт согласия, не дробить на три.

## §2. Backend

`app/routers/me.py` — рядом с `_get_or_create_user`/`UserDep`, тот же
файл, тот же паттерн (апсерт на каждый запрос уже есть для
`email_verified` — не изобретать второй механизм).

IP/UA — не новая механика, `get_client_ip(request)` уже есть и
используется в `rate_limit.py`/`deals.py`/`deals_public.py` — тот же хелпер,
не второй.

Версия документов — константа, не хардкодить в трёх местах:

```python
CURRENT_TERMS_VERSION = "2026-08-01"  # дата публикации TASK_fix20.md, поправь
                                    # владелец скажет актуальную когда впишет
                                # плейсхолдеры в сами документы
```

Новый эндпоинт — `request: Request` в сигнатуре, тот же паттерн что
в `create_deal` из E7:

```python
@router.post("/me/accept-terms", status_code=204)
async def accept_terms(user: UserDep, request: Request) -> None:
    uid = user["firebase_uid"]
    entry = {
       "version": CURRENT_TERMS_VERSION,
        "accepted_at": datetime.now(timezone.utc).isoformat(),
        "ip": get_client_ip(request),
        "ua": request.headers.get("user-agent", "")[:300],
    }
    pool = get_pool()
    async with pool.acquire() as conn:
        await conn.execute(
            "UPDATE users SET terms_acceptance_log = terms_acceptance_log || $1::jsonb WHERE firebase_uid=$2",
            json.dumps(entry), uid,
        )
```

Гейт-проверка (надо ли показывать экран) — не «журнал пустой», а
«последняя запись в журнале имеет `version == CURRENT_TERMS_VERSION`» — так
старые записи не мешают переспрашивать при смене версии.

Как фронт узнаёт что показывать гейт — либо `_get_or_create_user` уже
возвращает `terms_acceptance_log` из БД (он и так делает `RETURNING` со
всей строкой — просто добавить поле в `RETURNING`), и это отдаётся
клиенту через любой эндпоинт что уже вызывается сразу после логина.
Если такого эндпоинта сейчас нет (гейт email-верификации может быть
чисто клиентский, через `firebaseUser.emailVerified` из Firebase SDK, без
бэкенд-похода) — тогда нужен маленький `GET /v1/me` который отдаёт
`{email_verified, terms_accepted: bool}` (вычисляется из последней записи
журнала, не отдавать весь журнал целиком без нужды). Посмотри как
сейчас реально работает экран «Подтвердите email» перед тем как
выбирать — не дублировать логику, если она уже есть.

## §3. Frontend — блокирующий экран

Тот же визуальный паттерн что уже есть у «📧 Подтвердите email» —
дублировать вёрстку, не выдумывать новую. Условие показа: пользователь
аутентифицирован (прошёл email-верификацию, если она обязательна до
этого шага — порядок на твоё усмотрение) И последняя запись в
`terms_acceptance_log` либо отсутствует (пустой массив), либо её `version`
не совпадает с `CURRENT_TERMS_VERSION`.

Содержание экрана: чекбокс + текст «Я принимаю [Оферту](/terms),
[Политику конфиденциальности](/privacy) и [Cookie-политику](/cookies)»
(три ссылки, `target="_blank"`, как в футере) + кнопка «Продолжить»,
задизейблена пока чекбокс не отмечен. По клику — `POST /v1/me/accept-terms`,
затем пропустить в кабинет.

Опционально, не обязательно: тот же чекбокс можно продублировать прямо
в форме регистрации email/пароль для красоты UX — но это **не отменяет**
пункт выше. Вход через Google не проходит через форму регистрации
вообще (редирект и обратно уже авторизован), так что без блокирующего
экрана после аутентификации Google-пользователи вообще не увидят
условия ни разу. Экран из этого параграфа — обязателен, чекбокс в форме
— нет.

## §4. Существующие пользователи — ничего специально делать не нужно

Новая колонка `[]` у всех, включая тех кто уже зарегистрирован до
сегодняшнего дня. Условие показа гейта (пустой журнал или версия
последней записи не совпадает) само накрывает их при следующем логине —
отдельной миграции данных или email-рассылки не требуется (и не могли бы
— ADR-010, никаких backend-рассылок).
