# TASK: E1 Hotfix — Dockerfile без `nanoid`, упал `deploy-test.yml #33`

## Контекст

E1 закрыт кодом, PR смёржен в `main`, `ci.yml` зелёный.
После мержа автоматически запустился `deploy-test.yml #33` — упал на шаге
«Deploy to Cloud Run (test)» с `exit code 1`.

**Причина найдена без чтения логов (по коду):**

`C:\work\signfinder-api\Dockerfile` устанавливает Python-зависимости
захардкоженным списком в `RUN pip install --no-cache-dir "fastapi>=..." ...`,
**не из `pyproject.toml`**. Кодер (ты в предыдущей фазе E1) добавил
`nanoid>=2.0` в `pyproject.toml`, но в Dockerfile — забыл.

Последовательность падения:
1. Cloud Build собирает образ по `cloudbuild-test.yaml` → docker build по Dockerfile
2. Образ собирается без `nanoid` (в списке `pip install` его нет)
3. `gcloud run deploy` заменяет ревизию
4. Контейнер стартует → `app.main` импортирует `app.routers.deals`
5. `deals.py` (или `app.utils.share_token`) импортирует `from nanoid import generate`
6. `ModuleNotFoundError: No module named 'nanoid'`
7. Cloud Run уходит в crash loop
8. Smoke на `/health` возвращает не-200 → job падает

Это симптом более широкой дыры — Dockerfile сирота от `pyproject.toml`,
каждое добавление зависимости требует двойной правки в двух местах.
Рефактор — отдельным TASK, не в этом хотфиксе.

## §2. Задача — минимальный фикс

### 2.1 Правка `Dockerfile`

Открыть `C:\work\signfinder-api\Dockerfile`. В блоке:

```dockerfile
RUN pip install --no-cache-dir \
    "fastapi>=0.115" \
    "uvicorn[standard]>=0.32" \
    "python-multipart>=0.0.12" \
    "httpx>=0.27" \
    "pydantic>=2.5" \
    "firebase-admin>=6.5" \
    "asyncpg>=0.29"
```

Добавить строкой (с продолжением `\`):

```dockerfile
    "nanoid>=2.0"
```

**Больше ничего в Dockerfile не менять.** Это хотфикс, не рефактор.
Рефактор на `pip install .` — отдельный TASK (см. §4).

### 2.2 Сверка со `pyproject.toml`

Перед пушем сравни визуально:
- список `dependencies` в `pyproject.toml`
- список `pip install` в Dockerfile

Если найдёшь ещё расхождения (не только `nanoid`) — **не чини их в этом
хотфиксе**. Задокументируй в отчёте, пометь в BACKLOG как «дыра
Dockerfile ↔ pyproject.toml, чинить отдельным TASK». Владелец решит
когда чинить рефакторно.

Если найдёшь **критичное** расхождение (что-то без чего сервис не
стартует прямо сейчас на test) — тогда ЧАСТЬ хотфикса, добавляй в тот же
коммит с комментарием. Критерий «критичного»: попробуй мысленно
запустить `docker run` собранного образа — импортится ли `app.main`
без ошибок.

## §3. Workflow фикса

- Ветка: догоняем в существующей `feature/e1-deals-model` (не новая).
  PR уже смёржен, но ветка не удалена — либо чекаутишься в неё и
  пушишь новый коммит (что поднимет CI и деплой заново), либо создаёшь
  hotfix-ветку `hotfix/e1-dockerfile-nanoid` от `main` и открываешь
  новый PR.
- **Уточни у владельца** какой вариант предпочитаемее ДО пуша.
  По ADR-008 pushes в main запрещены, значит вариант 2 (новый PR) —
  по умолчанию правильный. Но если ветка E1 ещё жива и она — просто
  ускорит.
- Push → `ci.yml` (~3-5 мин) → merge (владелец) → `deploy-test.yml`
  (~5-7 мин).

### 3.1 Мониторинг деплоя — часть задачи

**Ты (не владелец) мониторишь `deploy-test.yml` до успеха.**

- Используй `gh run watch` или `gh run view --log-failed` — те же инструменты,
  которыми ты уже пользовался в E1.
- Если `deploy-test.yml` снова падает — **не эскалируешь владельцу**, а
  разбираешь причину через `gh run view --log-failed`, чинишь тем же
  циклом (правка → push → watch).
- Если после 3 итераций разобрать не получается — **тогда** приносишь
  владельцу текст failed job и подробный отчёт что пробовал.
- **Не завершай задачу пока `deploy-test.yml` не зелёный и test-контур
  не отдаёт `/v1/version` с `api_version: 1.19.0`.**

Это правило исправляет дыру TASK-шаблона E1, где кодер отчитался
«PR открыт» и вышел из активной фазы до фактического деплоя. См.
§Journal 2026-07-24 в GIT_WORKFLOW.md — там описан этот урок.

## §5. Что делать НЕ надо

Всё из GIT_WORKFLOW § Явные запреты плюс:

- **Не рефакторить Dockerfile под `pip install .`** — это хотфикс, минимальная
  правка одной строки. Рефактор — отдельный TASK.
- **Не менять cloudbuild-test.yaml, deploy-test.yml, ci.yml** — они рабочие.
  Проблема в Dockerfile, не в пайплайне.
- **Не эскалировать владельцу «примени руками», «добавь зависимость через
  Cloud Console»** — фикс через код и git flow, как всегда.
- **Не начинать E2** пока хотфикс E1 не долетел до test-контура и
  test-контур не подтвердил `/v1/version` = 1.19.0.
- **Не деплоить на prod** — E1 в целом не деплоится на prod до тех пор пока
  не собрана вся цепочка Deal Cycle до E4 (см. общий план релиза).
