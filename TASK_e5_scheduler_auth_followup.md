# TASK: E5 — Cloud Scheduler не может передать Authorization заголовок через gcloud CLI

## Контекст

Код E5 полностью готов и подтверждён: оба внутренних эндпоинта
(`/internal/deals/expire-sweep`, `/internal/deals/purge-old`) существуют,
защищены `ApiKeyDep`, корректно отвечают `401` без валидного токена — то
есть логика авторизации на стороне API работает правильно.

**Проблема — не в коде, а в проводке Cloud Scheduler → заголовок.**
Владелец руками провизионировал задания (`gcloud scheduler jobs create
http` / `update http`) с `--headers`/`--update-headers` для
`Authorization: Bearer <api-key>`. Воспроизведено дважды разными
методами:

1. `gcloud scheduler jobs update http <name> --update-headers="Authorization=Bearer $key"`
   → задание обновляется без ошибки, но `gcloud scheduler jobs describe`
   показывает `Authorization: 'Bearer '` — значение не сохранилось
2. `gcloud scheduler jobs delete <name>` + `gcloud scheduler jobs create
   http <name> --headers="Authorization=Bearer $key"` (пересоздание с
   нуля, не update) → та же картина, значение снова пустое

Оба раза `$key` в PowerShell была подтверждённо непустой строкой
(`.Length` = 48 перед вызовом команды) — то есть проблема не в
PowerShell-переменной, а где-то между gcloud CLI и Cloud Scheduler API
именно для заголовка `Authorization`.

**Рабочая гипотеза (не проверена):** GCP может резервировать заголовок
`Authorization` для собственного механизма OIDC/OAuth авторизации Cloud
Scheduler → Cloud Run (`--oidc-service-account-email`), и молча его
обнуляет когда он передаётся как обычный custom-header. Это не точно —
не подтверждено официальной докой, только по поведению.

**Живое состояние на момент паузы:**
- `signfinder-cab-test`: секрет `api-key` **ротирован** (версия 2, был
  `placeholder` → теперь случайное 48-символьное значение). Cloud Run
  подхватил (ревизия `signfinder-api-00077-8c8`). Оба Scheduler-задания
  существуют, `state: ENABLED`, но с пустым `Authorization`
- `signfinder-prod`: секрет `api-key` **не менялся** (не был
  `placeholder`, но НЕ ротирован в рамках этого инцидента — если нужно
  ротировать, это отдельное решение владельца). Все 4 Scheduler-задания
  существуют, та же проблема с пустым заголовком

## §2. Задача — найти рабочий способ провизионирования

Три направления на выбор, не обязательно все:

**A. Проверить гипотезу про резервацию `Authorization`.** Поискать в
актуальной документации Cloud Scheduler (веб-поиск, не из памяти —
могло измениться) подтверждение или опровержение. Если резервация
подтвердится — это меняет архитектуру: нужен либо OIDC (см. вариант B),
либо кастомный заголовок вместо `Authorization`.

**B. Альтернатива — Cloud Scheduler OIDC вместо статичного заголовка.**
Вместо `Authorization: Bearer <API_KEY>` — Cloud Scheduler подписывает
запрос OIDC-токеном от имени служебного аккаунта
(`--oidc-service-account-email`), эндпоинт верифицирует токен через
`google-auth` библиотеку. Не требует передавать секрет в заголовке
вообще, GCP делает это сам. Требует:
  - Новый минимальный service account (например
    `deals-cron-invoker@signfinder-cab-test.iam.gserviceaccount.com`)
  - Код на верификацию OIDC-токена в новом эндпоинте (или отдельная
    dependency рядом с `ApiKeyDep`, не заменяя её — старые внутренние
    роуты пусть остаются на `ApiKeyDep`)
  - `google-auth` в зависимостях (проверить, возможно уже подтягивается
    транзитивно через `firebase-admin` — сверить в `pyproject.toml` +
    **обязательно Dockerfile**, см. GIT_WORKFLOW §Известные технические дыры)

**C. Кастомный заголовок вместо `Authorization`.** Если проблема
специфична именно для имени `Authorization` — переименовать в
что-то вроде `X-Deals-Cron-Key`, эндпоинт проверяет его вместо
`Authorization: Bearer`. Минимальная правка кода (новая dependency,
похожая на `verify_api_key`, но читающая другой заголовок), не трогает
инфраструктуру Scheduler вообще.

**Рекомендация (не обязательная к исполнению, оцени сам):** C — самый
дешёвый путь, если гипотеза A подтвердится. Не создаёт нового SA, не
требует OIDC-верификации в коде. Если A не подтвердится (то есть
`Authorization` не резервирован, а проблема в чём-то другом) — тогда
это не поможет, разбираться дальше.
